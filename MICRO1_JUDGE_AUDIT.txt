RepoAudit — Strict Micro1 Judge Audit
======================================
Written as the harshest reasonable reading of the actual brief (rubric,
ground rules, four questions, four deliverables) against the CURRENT state
of the repo, mid-Phase-2, as of this snapshot. Every item below is either
verified against the repo's actual current files or an honest interpretive
risk, not invented. Ordered roughly worst-first.

INSTANT-FAIL-RISK: MISSING REQUIRED DELIVERABLES (if judged right now)
------------------------------------------------------------------
- The brief lists 4 required final deliverables. As of this snapshot, 3 of 4
  do not exist at all:
  * No top-level README.md. Deliverable #1 explicitly requires it to
    "introduce the intended user," "explain their current bottleneck," and
    carry a labeled "Improvement Changelog." We have changelog.md and
    problem.md separately, but not the single README the brief asks for.
  * No REPRODUCTION.md and no scripts/run_all.py (deliverable #2). A judge
    right now has ZERO documented path to reproduce anything.
  * No solution video (deliverable #3). Not startable until the pipeline is
    feature-complete; real risk given the event ends tomorrow.
- outputs/trajectories/ EXISTS BUT IS EMPTY (checked directly). Deliverable
  #4 requires "representative trajectories for every agent you used... from
  the agent instructions to the final result... tool calls... retries...
  human checkpoints." We have already RUN two full agents (baseline, iter1)
  and have raw responses sitting in outputs/baseline/*.json and
  outputs/iter1/*.json, but none of it has been shaped into the trajectory
  format the brief wants, and none of it lives in outputs/trajectories/ yet.
  A judge grading strictly could call this "deliverable not met" even though
  the underlying data exists.

GROUND RULE VIOLATIONS / RISKS (the brief calls these "baseline
requirements for every eligible project" — not optional)
------------------------------------------------------------------
- Rule #8 "Keep credentials and private information outside the submission."
  A live NVIDIA API key was pasted in plaintext directly into this chat
  session by the user. It is correctly NOT committed to git (verified:
  `git ls-files` shows .env is untracked) and .gitignore correctly excludes
  it. BUT: the key now exists in plaintext in this conversation's history.
  If any chat log, screenshot, or export of this session is ever included
  anywhere near the submission (even accidentally, e.g. in a shared folder,
  a demo recording that shows a terminal scrollback, or a support ticket),
  that's a direct rule #8 violation with a live credential exposed. Hard
  recommendation: rotate this key before submission regardless of whether
  it's ever actually exposed, purely because it was said aloud once.
- Rule #4 "Keep consequential actions controlled through a sandbox or
  simulation. Add human approval before the action happens." Currently (end
  of Phase 2) there is NO human-approval gate anywhere in the pipeline
  before a finding is written to the final report. Phase 5 (not yet built)
  is supposed to add exactly this. Until it exists, a strict reading is:
  the current pipeline can accuse a real, named paper's real, named authors
  of a specific reproducibility failure (data leakage, etc.) and publish
  that report with zero human review step. That is a real-world-consequential
  action (reputational) with no approval gate. Fails this rule as currently
  built; only resolved once Phase 5 ships.
- Rule #5 "Make a qualified human reviewer part of any solution that could
  significantly affect someone." Same underlying gap as above — a false
  positive naming a real paper as leaking data is exactly the kind of thing
  that "could significantly affect someone" (the paper's authors). No human
  reviewer step exists yet.
- Rule #3 "Use every tool and component according to its license and service
  terms." We never explicitly checked: (a) NVIDIA NIM's terms of service for
  hackathon/automated-audit use at this volume, (b) whether feeding the full
  text of someone else's GitHub repo through a third-party LLM API is
  consistent with that repo's license. Several eval-set repos DO have
  LICENSE files (cifar_10_100n, lottery_ticket_hypothesis,
  birt_continual_learning, network_deconvolution, sample_specific_masks,
  and the dropped fairness_demographic_shift) that were never actually read
  or logged. Likely fine (research code, typically permissive licenses) but
  "likely fine, never checked" is not the same as "verified," and a strict
  judge can dock this.
- Rule #2 "Make it clear what existed before the competition and what you
  added." No document currently states this explicitly and up front. It's
  implicit in code comments and citations, but the brief wants this stated
  clearly (e.g. "we built: the audit pipeline, eval harness, ground truth,
  synthetic fixture. We used as-is: LangGraph, NVIDIA NIM models, the 8
  external repos as unmodified test subjects"). Missing until README exists.
- Rule #9 "Connect every claim about your results to the evidence you
  submit." Mostly done well (every ground-truth finding cites file:line and
  a real quote) — but the "48 hours per paper, 41.4% completion" PaperBench
  statistic used throughout problem.md and instructions.md was never
  independently re-verified against the actual PaperBench paper in this
  session; it was carried over from instructions.md's own text. That's
  citing a citation, not verifying a source. A strict judge could ask "did
  you check this yourself?" and the honest answer right now is no.

RUBRIC-CRITERION-BY-CRITERION FAULTS
------------------------------------------------------------------
Problem & User Value (15 pts)
- "Who has this problem" is answered with a generic persona (journal
  editors / PC chairs / team leads), not a real named user or a direct
  quote from someone who's actually said "I need this." Everything is
  inferred from published benchmark papers, not primary user research. A
  judge could reasonably say the user need is asserted, not demonstrated.

Agent Solution & Engineering (30 pts) — the single biggest point bucket
- Only 2 of the 5 planned iterations exist (baseline, extractor+verifier).
  Phase 3 (real tools: grep/AST/config), Phase 4 (6 specialized checkers),
  and Phase 5 (consensus + human gate) are all still unbuilt. If time runs
  out, "Agent Solution & Engineering" gets judged on a fraction of the
  planned design.
- We confirmed NVIDIA NIM's hosted endpoint returns HTTP 400/500 on both
  guided-JSON structured output AND tool/function-calling for our primary
  model (tested directly, not assumed). Phase 3's plan explicitly calls for
  "a ReAct-style agent that can call these tools" — real tool-calling. If
  the backend can't do native tool-calling reliably, Phase 3 has to fall
  back to a manual prompt-parse-execute-reprompt loop, which is more custom
  code, more surface area for bugs, and weaker "engineering" evidence than
  clean native tool use would have been.

End-to-End Quality (20 pts) — "the finish of something a person would sign
their name to rather than an obvious AI generated draft"
- Every output artifact that exists right now (outputs/baseline/*.txt,
  outputs/iter1/*.txt) is a raw developer/debug log — file-path dumps,
  JSON blobs, error strings. Nothing has been designed for the actual
  stated end user (a PC chair with 15 minutes). There is currently no
  "final report" format meant for a human who isn't debugging the pipeline.
  This is arguably the single biggest quality gap right now: we've built a
  measurement harness, not yet a product.

Measured Improvement (15 pts)
- The brief says "Choose ONE primary metric that reflects what success
  means to the user." We built a multi-metric dashboard (precision, recall,
  F1, severity-weighted precision, FPR-on-clean, per-failure-mode
  breakdown) with no single metric explicitly designated as THE headline
  number. A strict judge could read this as not following the instruction
  as given, even though the underlying data is arguably more rigorous.

Reproducibility (15 pts)
- No REPRODUCTION.md, no run_all.py, as stated above.
- Reproduction depends on cloning 8 external GitHub repos live at judging
  time. If any one of them is deleted, renamed, or made private between now
  and judging, that paper's reproduction breaks and this is currently
  undocumented as a risk anywhere.
- NIM free-tier credit balance was never confirmed (flagged in
  phase_0_setup.md). If credits run out mid-run during judging, the
  reproduction fails partway with no documented fallback.
- The eval set is 9 papers, not the "ten or more" the brief calls "a good
  target when the task allows it." Logged honestly throughout, but still a
  real, nameable gap against the brief's own stated preference.

Hot Take / Insights (5 pts)
- Not written yet. Lowest point value, lowest risk, but currently zero.

"ONE CHALLENGING CASE" (explicitly called out in the four-question
framework and rubric)
------------------------------------------------------------------
- The brief's own worked example ("Candidate evaluation") explicitly models
  "one candidate with conflicting signals" as a real, load-bearing part of
  reproducing the result. instructions.md's own plan for this was "one repo
  where you'll plant a known defect" — i.e., a real production repo with a
  deliberately injected bug. That category (C) was explicitly skipped by
  direction. What exists instead is a wholly synthetic, small (~90-line)
  sklearn toy script. It correctly plugs the ground-truth gap for scoring
  purposes, but a strict judge could reasonably say a synthetic toy fixture
  is a materially weaker "challenging case" than a real, complex, planted
  bug in production-scale code would have been — the brief's own examples
  suggest more.

PROCESS / HOUSEKEEPING FAULTS (small individually, they add up)
------------------------------------------------------------------
- `.claude/` (local tool state, e.g. scheduled_tasks.lock) is NOT in
  .gitignore and currently shows as untracked-but-present. Should be
  ignored; as-is, risks getting swept into a careless `git add -A` and
  committed as noise that has nothing to do with the project.
- data/repos/fairness_demographic_shift/ is a leftover clone from a
  candidate paper that was investigated and DROPPED (no arXiv HTML, PDF
  blocked by OpenReview's bot protection). It's gitignored so won't be
  committed, but it's dead local clutter that could confuse anyone poking
  around the working tree, including a judge with terminal access.
- `estimated_nim_credits` is `null` in every _summary.json by design (the
  $/credit rate was never confirmed) — correctly honest, but if a judge
  skims the JSON without reading the caveat in phase_0_setup.md, it reads
  as "this project didn't bother tracking cost," when the real story is
  "tracked precisely in tokens, deliberately didn't fabricate a dollar
  figure it couldn't verify." Worth surfacing this distinction explicitly
  wherever cost is discussed in the final README, not just buried in a
  Phase 0 known-issues list.
- Extracted "confidence" scores on every finding are currently decorative —
  nothing in src/eval.py's scoring logic uses them (only "severity" feeds
  the severity-weighted-precision metric). A judge reading the code closely
  could ask "why compute this if it's unused."

TIMELINE RISK (not a rubric line item, but existential)
------------------------------------------------------------------
- Event ends 2026-08-31. As of this audit: Phases 3, 4, 5 unbuilt; README,
  REPRODUCTION.md, run_all.py, video, and trajectory files all unbuilt. That
  is the majority of the required deliverables, on a one-day runway. Every
  fault listed above is fixable, but only if there's enough clock left to
  fix it — this is the actual binding constraint, not any single design
  flaw above.

BOTTOM LINE
------------------------------------------------------------------
Nothing above is a fabrication or a stretch — every item traces to a real,
checked file (or its absence) or a direct quote from the brief. Most of it
is "not done yet, on a known plan" rather than "done wrong." The two items
that would worry a genuinely strict judge most, independent of remaining
time, are: (1) no human-approval gate yet for a tool that can publish
reputationally-consequential claims about real people's real work (rules
#4/#5), and (2) the live API key having been spoken in plaintext into this
session at all (rule #8), regardless of the fact it's correctly kept out of
git. Everything else is a matter of finishing the plan already on paper.
